# Медиа без Redis и VPS

Все новые изображения из админки (обложки, сторис, образование, отзывы и SEO)
обрабатывает одна очередь PostgreSQL. Бинарные данные хранятся на диске, в базе —
метаданные, состояние и ссылки на варианты. Redis не входит в рабочий граф API:
сессии, CSRF-основа сессии и ограничения запросов также используют PostgreSQL.

## Загрузка и восстановление

1. Админка вычисляет SHA-256 и создаёт запись с UUID, размером, назначением и
   контекстом формы. Повтор с тем же UUID идемпотентен только при совпадении файла.
2. Файл передаётся бинарными частями по 1 МиБ. Авторизация, CSRF и лимиты проверяются
   до чтения тела. Файлы лежат в закрытом `private/<id>`; одинаковые части можно
   повторять, конфликтующие отклоняются.
3. `/complete` проверяет наличие всех частей, размер и SHA-256, сохраняет исходник
   и переводит запись в `QUEUED`. С этого момента браузер для обработки не нужен.
4. Cron последовательно обрабатывает задания. Глобальная аренда на 120 секунд
   предотвращает параллельные запуски. У задания есть собственная аренда и токен;
   поздний результат прежнего исполнителя не публикуется. Временные ошибки
   повторяются через минуту, максимум три попытки. Повтор доступен в админке.
5. Готовность и запись `story_media` фиксируются одной транзакцией после записи
   всех вариантов. Файлы попыток имеют разные URL. Старое изображение не заменяется
   до выбора готового результата и сохранения формы.

При обрыве до `/complete` нужно снова выбрать тот же файл: браузер хранит UUID
загрузки в localStorage и сервер возвращает принятые части. Если localStorage очищен
или используется другой браузер, потребуется новая загрузка. Загрузка не идёт в
закрытом браузере. Уже принятые файлы и очередь доступны через «Загруженные файлы»
после перезагрузки. Остальные несохранённые изменения формы автоматически не
восстанавливаются; медиа можно снова выбрать из списка и сохранить форму.

## Профили

| Назначение            | Основной файл                                 | Остальные варианты         |
| --------------------- | --------------------------------------------- | -------------------------- |
| Фото и обложка статьи | WebP quality 90, до 2560 × 2560, вписывание   | до 960 × 960 и 320 × 320   |
| Фото сторис           | WebP quality 90, до 1080 × 1920, вписывание   | до 540 × 960 и 240 × 426   |
| Документы и скриншоты | Lossless WebP, до 2560 × 2560                 | WebP quality 90, 960 и 320 |
| Социальные превью     | JPEG quality 90, рамка 1200 × 630 без обрезки | 600 × 315 и 240 × 126      |

Поворот EXIF учитывается, метаданные исходника в результат не переносятся.
Маленькие изображения не увеличиваются. Анимация и повреждённые файлы отклоняются.
Исходные фото: JPG/PNG/WebP до 8 МиБ и 40 млн пикселей. Один процесс Sharp,
один поток libvips, кэш 16 МиБ, таймаут одного варианта 15 секунд. Кэш не является
общим пределом памяти процесса: максимальный допустимый файл нужно измерить на
выбранном тарифе NetAngels. Короткий запуск берёт новые задания в течение 25 секунд
и заканчивает уже начатое; три варианта могут занять до 45 секунд.

Видео принимается только для сторис: готовый MP4 H.264 (`avc1`) и необязательный
AAC-LC (`mp4a.40.2`), не более 30 МиБ, 60 секунд, 60 кадров/с, 1920 × 1080 или
1080 × 1920. Требуется быстрый старт (`moov` перед медиаданными). MP4Box проверяет
структуру, кодеки, параметры и наличие заявленных сэмплов; видео не перекодируется.
Произвольные HEVC/WebM/4K требуют предварительной подготовки вне хостинга.

## Cron и размещение

- `MEDIA_DIRECTORY` — абсолютный постоянный каталог вне релизов; для NetAngels
  `app/shared/media`. Стабильные `start.cjs` и `media-cron.cjs` устанавливают этот
  путь по умолчанию. Локально используется `backend/var/media`.
- Команда разработки: `pnpm media:process` из `backend`.
- Команда NetAngels: `node /home/cXXXX/api.example.ru/app/media-cron.cjs`.
  В панели cron: `* * * * *`, Node 24 в окружении сайта. Нельзя запускать через HTTP.
- Деплой устанавливает команду, но не создаёт задание в аккаунте NetAngels.
- `pnpm demo:tunnel --local` запускает тот же одноразовый обработчик раз в 10 секунд
  для демонстрации. API не запускает тяжёлую обработку самостоятельно.
- API отдаёт `public` по `/media` с долгим immutable-кэшем и Range. Для прямой отдачи
  nginx NetAngels можно связать `www/media` Node-сайта с `app/shared/media/public`;
  приватный каталог нельзя помещать в `www`. Это настраивается в аккаунте хостинга.
- `/v1/story-media/<id>` сохраняется для совместимости; `?variant=preview`,
  `mobile` и `optimized` перенаправляют на готовые варианты. Старые оригиналы
  сохраняют прежние байты и URL. Карточки, дипломы и кружки сторис берут меньшие версии.

Исходники и части успешных новых загрузок удаляются через семь дней, метаданные и
готовые версии сохраняются. Непривязанные готовые файлы автоматически не удаляются:
они нужны для восстановления после перезагрузки. Неиспользованные результаты
неудачных попыток удаляются через семь дней. Незавершённая передача через семь дней
получает `UPLOAD_INCOMPLETE`. Суммарный лимит зарегистрированных исходных файлов —
1 ГиБ; это резерв для маленького диска, а не точная квота файловой системы.
Нужны контроль свободного места и совместная резервная копия PostgreSQL и каталога
медиа. Бэкап одной базы больше не содержит новые изображения.

## Старые файлы

Перед переносом сделать резервную копию базы и медиа. Команда
`pnpm media:process --import-legacy` переносит до 20 старых файлов из `story_media`
на диск за запуск и ставит изображения в очередь; повторять до `Imported 0`.
На хостинге используется `node /home/cXXXX/api.example.ru/app/media-cron.cjs --import-legacy`.
Старые видео копируются без перекодирования. Исходные байты старых публичных файлов
сохраняются на диске: это поддерживает ранее опубликованные immutable-URL.
Изображения, импортируемые через Astro Image/getImage, оптимизируются при сборке.
Файлы из public, подключённые обычным URL (например, старые дипломы), эта очередь
автоматически не меняет: для перевода в новый подход их нужно загрузить через
админку. Все новые загрузки и замены используют общую очередь.
