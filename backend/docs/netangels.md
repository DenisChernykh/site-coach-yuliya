# Размещение на NetAngels

Проект использует управляемый хостинг NetAngels: один сайт Node.js для NestJS и React-админки,
PostgreSQL и Redis контейнера, отдельный статический сайт для Astro. Сборки
выполняются в GitHub Actions. Docker нужен для локальных проверок и CI.

## Тариф и требования

Калькулятор хостинга проверен 11 октября 2026 года: при 5 ГБ диска и помесячной
оплате «Базовый» с 512 МБ стоит 199 ₽/месяц, «Продвинутый» с 1 ГБ — 297 ₽,
«Эксперт» с 2 ГБ — 493 ₽. Рекламные 179 ₽ относятся к оплате за год.
Это цены конфигураций калькулятора; дополнительные услуги и домен оплачиваются
отдельно. Для начала предлагается 1 ГБ, с проверкой фактического потребления
после запуска. Возможность работы под нагрузкой на конкретном контейнере
пока не измерена.

Источники: [тарифы](https://www.netangels.ru/hosting/),
[возможности хостинга](https://www.netangels.ru/support/cloud-hosting/overview/),
[Node.js](https://www.netangels.ru/support/cloud-hosting/node/),
[PostgreSQL](https://www.netangels.ru/support/cloud-hosting/postgresql/),
[API хостинга](https://api.netangels.ru/modules/gateway_api.api.hosting.routes.virtualhosts/).

Redis на этом хостинге хранит данные в памяти. Его перезапуск завершит сессии
администраторов и сбросит краткосрочные ограничения частоты запросов. Заявки,
согласия, контент и обе очереди находятся в PostgreSQL и сохранятся.

## Однократная настройка хостинга

1. Создать сайт `api.example.ru` с технологией Node.js **24.x**, одним воркером,
   PostgreSQL **14+** и HTTPS. Включить Redis контейнера. Создать отдельный сайт
   `example.ru` с технологией «Статический сайт» и HTTPS.
2. Проверить SSH-доступ контейнера и разрешить ключ GitHub Actions. Сверить
   отпечаток SSH-сервера и сохранить строку `known_hosts` для этого адреса.
3. В каталоге API создать `app/shared`, сохранить `netangels.env.example` как
   `app/shared/.env`, установить права `600` и заполнить значения. Четыре секрета
   авторизации генерируются независимо. `DATABASE_URL` можно взять из панели;
   если она отсутствует, код использует `DB_CONNECTION_STRING` хостинга.
4. Заполнить `TRUST_PROXY_CIDRS` точными адресами reverse proxy NetAngels,
   полученными из панели или поддержки. Это необходимо для корректного IP
   пользователя, ограничений формы и защищённых cookies. Добавить origin публичного сайта и API в
   `CORS_ORIGINS`. Для www также добавить его origin и настроить перенаправление
   на основной домен.
5. Установить **pnpm 11.15.1** в пользовательском окружении Node.js сайта.
   Команда `pnpm --version` после перехода в каталог сайта должна возвращать
   эту версию. Деплой использует интерактивный bash, чтобы активировалось
   виртуальное окружение NetAngels при `cd` в каталог сайта.
6. В параметрах Node.js установить `APP_PATH` в абсолютный путь
   `/home/cXXXX/api.example.ru/app/start.cjs`. `APP_IP` и `APP_PORT` оставить
   значениями хостинга: приложение использует их автоматически.
7. Статический `www` должен отсутствовать перед первым деплоем либо быть
   ссылкой на `.site-releases/<release>`. Существующий каталог с нужными файлами
   сначала сохранить под другим именем. Деплой откажется заменять обычный
   каталог. Отключить длительный кэш HTML и `release.json` в панели.

Runtime-зависимости устанавливаются на хостинге, чтобы нативный Argon2
соответствовал его ОС. TypeScript и Astro собираются на CI. `.env` остаётся
в `shared` и подключается ссылкой к каждой версии приложения.

## GitHub: кнопка деплоя

Workflow находится в корне репозитория: `.github/workflows/deploy-netangels.yml`.
Он должен быть закоммичен в основную ветку GitHub, чтобы была доступна кнопка
**Actions → Deploy to NetAngels → Run workflow**. Выбор `all`, `backend` или
`site` позволяет выложить всё, API вместе с админкой или только пересобранный сайт.
React собирается в CI и входит в тот же релиз бэкенда. Интерфейс доступен
по `https://api.example.ru/admin/`; cookie и запросы API используют этот origin.
Возврат к предыдущему релизу бэкенда возвращает также соответствующую сборку админки.
Запуски последовательно обслуживает одна группа `netangels-production`.

Создать GitHub Environment **production** и разрешить доступ к нему только
ветке, из которой выполняется публикация. Если нужны автоматические сборки
контента без ручного подтверждения, не добавлять обязательного ревьюера для
каждого запуска этого environment.

Variables environment:

| Имя                        | Пример / значение                       |
| -------------------------- | --------------------------------------- |
| `NETANGELS_SSH_HOST`       | SSH-адрес контейнера из панели          |
| `NETANGELS_SSH_USER`       | `cXXXX`                                 |
| `NETANGELS_SSH_PORT`       | `22`, если панель не указывает другой   |
| `NETANGELS_API_DOMAIN`     | `api.example.ru`                        |
| `NETANGELS_SITE_DOMAIN`    | `example.ru`                            |
| `NETANGELS_API_SITE_ID`    | числовой ID Node.js сайта из API/панели |
| `NETANGELS_STATIC_SITE_ID` | числовой ID статического сайта          |
| `NETANGELS_APP_DIR`        | `/home/cXXXX/api.example.ru/app`        |
| `NETANGELS_WWW_DIR`        | `/home/cXXXX/example.ru/www`            |
| `PUBLIC_API_URL`           | `https://api.example.ru`                |
| `PUBLIC_SITE_URL`          | `https://example.ru`                    |

Secrets environment:

| Имя                         | Назначение                                                |
| --------------------------- | --------------------------------------------------------- |
| `NETANGELS_SSH_PRIVATE_KEY` | отдельный приватный SSH-ключ деплоя                       |
| `NETANGELS_SSH_KNOWN_HOSTS` | заранее проверенная запись хоста                          |
| `NETANGELS_API_KEY`         | API-ключ панели для проверки целевого сайта и перезапуска |
| `INITIAL_ADMIN_EMAIL`       | логин первого администратора                              |
| `INITIAL_ADMIN_PASSWORD`    | пароль не короче 12 символов                              |

При первом запуске `all` включить `initialize_admin`. Пароль передаётся
процессу создания пользователя через stdin. Повторные деплои выполнять с
выключенным флагом: bootstrap отказывается создавать второго первого
администратора. Регистрация через сайт отключена.

Перед записью деплой проверяет ID, домен, тип сайта и Node.js 24 через API
NetAngels. Он загружает версию, устанавливает production-зависимости, применяет
миграции, один раз инициализирует контент и переключает символьную ссылку.
API перезапускается через `PUT /api/v2/hosting/virtualhosts/{id}/restart/`.
Проверка ожидает готовность именно нового commit SHA. При ошибке после
переключения восстанавливается предыдущая ссылка. При самом первом запуске
предыдущей версии ещё нет, поэтому автоматический откат невозможен.

Миграции назад автоматически не откатываются. Следующие миграции должны
сохранять совместимость предыдущей версии кода до завершения выкладки.
Версии на диске сохраняются для отката; периодически удалять старые после
проверки актуальной и предыдущей версий, чтобы укладываться в объём тарифа.

## Автоматическое обновление контента

В `shared/.env` задать `SITE_REBUILD_MODE=enabled`, `PUBLIC_SITE_URL`,
`GITHUB_REPOSITORY=owner/repository`, `GITHUB_PUBLICATION_REF` и
`GITHUB_ACTIONS_TOKEN`. Нужен fine-grained token только для этого репозитория
с разрешением **Actions: write**. Токен хранится на бэкенде и не передаётся
браузеру. Ветка должна совпадать с разрешённой веткой environment production.

Сохранение контактов, настроек, SEO, главной, FAQ, ссылок, статьи или программы
меняет общий черновик CMS. Кнопка «Опубликовать» атомарно переносит этот снимок
в публичные таблицы, увеличивает версию контента и ставит пересборку в очередь
PostgreSQL. Черновики остаются скрыты в публичном API до публикации.
Статусы и заметки заявок пересборку не запускают.

Через 30 секунд после последней публикации worker запускает тот же workflow с
`target=site`. Он проверяет результат GitHub и `release.json` публичного сайта.
При правке во время сборки планируется следующая сборка, поэтому новые изменения
не теряются. Ошибки повторяются до трёх попыток; ошибки прав доступа прекращают
запуски сразу. Статус виден сверху в админке и доступен в `GET /v1/admin/publication`, повтор —
`POST /v1/admin/publication/retry`. Во время ожидания и ошибки остаётся предыдущая
статическая версия. Сборка считывает версию до загрузки контента, поэтому
изменения во время сборки не считаются опубликованными раньше времени.

Статьи и другие данные становятся видны на сайте после успешной сборки и
выкладки. Это обычно минуты, точное время зависит от GitHub Actions и хостинга.
[Astro поддерживает статическую и серверную генерацию](https://docs.astro.build/en/guides/on-demand-rendering/);
для этого проекта выбран статический вариант без второго Node.js-процесса.
[GitHub API запуска workflow](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event)
используется с версией API `2026-03-10`, возвращающей ID запуска.

## Telegram и проверка после запуска

Бот проекта: [@yuliya_valishina_requests_bot](https://t.me/yuliya_valishina_requests_bot),
«Юлия Валишина · Заявки с сайта». Создан 11 октября 2026 года. Локальная
доставка включена в чат владельца, который запустил бота. Токен и ID получателя
сохранены в игнорируемом `backend/.env` с правами `600`; в Git их не добавлять.
При размещении на хостинге перенести настройки в `app/shared/.env`.

После передачи бота Юлии через BotFather она должна открыть бота и нажать
«Старт». Получить её числовой `message.chat.id` через Telegram API `getUpdates`,
записать его в `TELEGRAM_CHAT_ID` окружения, которое отправляет заявки, и
перезапустить бэкенд. Передача владения ботом не меняет получателя уведомлений.
Проверить новую тестовую заявку и статус `SENT` в админке. Если токен менялся,
обновить также `TELEGRAM_BOT_TOKEN`.

Заполнить `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` и
`TELEGRAM_NOTIFICATIONS_MODE=enabled`. Добавить бота в нужный чат и разрешить
ему отправку. Создание заявки и задачи уведомления происходит одной записью
в транзакции. Временные ошибки повторяются, ответ 429 учитывает `retry_after`;
после восьми попыток или постоянной ошибки задача получает `FAILED`.

Доставка имеет семантику «как минимум один раз»: если Telegram принял сообщение,
а процесс завершился до сохранения результата, повтор может отправить дубликат.
В сообщении есть постоянный номер заявки для его распознавания. Статус доставки
виден вместе с заявкой; повтор `FAILED` выполняется через
`POST /v1/admin/consultations/{id}/telegram/retry`.

Проверить `/health/ready`, вход администратора, тестовую заявку и её получение
в Telegram. Изменить опубликованный контент и дождаться `IDLE` с одинаковыми
`requestedRevision` и `deployedRevision`. Production Swagger `/docs` и
`/openapi.json` по умолчанию защищены сессией администратора. Реальные контакты,
реквизиты владельца и согласованный текст политики добавляются до запуска сайта.

Проверены локальная БД, HTTP-сценарии и адаптеры внешних API на управляемых
ответах. 11 октября 2026 года также проверена настоящая доставка: локальный
`POST /v1/consultations` принял тестовую заявку, бот прислал уведомление, а
бэкенд сохранил `SENT` после одной попытки с ID сообщения Telegram.
Подключение к конкретному аккаунту NetAngels и выполнение workflow в GitHub
требуют заполненных доступов; эти операции пока не выполнялись.
