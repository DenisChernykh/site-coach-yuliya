# Мониторинг production

Общий сервис находится в отдельном проекте `site-monitor`: Cloudflare Worker принимает безопасные события, D1 хранит историю, один бот уведомляет обо всех сайтах с указанием проекта. Внешние проверки запускает Cloudflare Cron. GitHub Actions только собирает и размещает приложение.

## Сайт, админка и backend

Сборщик JS-ошибок использует уже установленный Sentry SDK, но его transport отправляет JSON только нашему Worker. Sentry SaaS и HetrixTools не нужны. В SDK выключены tracing, replay, breadcrumbs, запросы, тела, cookie и клиентские отчёты. Перед отправкой и перед сохранением действует белый список полей: тип ошибки, код, версия сборки, request ID и координаты стека. Нельзя передавать в код события текст формы или произвольный текст исключения.

Переменные сборки сайта: `PUBLIC_MONITOR_URL`, `PUBLIC_MONITOR_KEY`, `PUBLIC_MONITOR_RELEASE`. Для админки те же с префиксом `VITE_`. URL заканчивается `/v1/browser/coach-yuliya`. Это публичный ключ только для приёма; он не даёт читать данные. Origin домена надо зарегистрировать в сервисе.

На backend: `MONITOR_URL` с путём `/v1/ingest/coach-yuliya`, секретный `MONITOR_KEY`, `SERVICE_REVISION`, `NODE_ENV=production`. Секрет backend не попадает в Vite/Astro. Ошибки отправляются с повторной попыткой; отказы коллектора не меняют результат пользовательской операции. При аварийном уничтожении процесса часть отправок может потеряться.

Завершения HTTP-запросов агрегируются по минутам в памяти процесса: количество, 5xx, сумма длительности и интервалы <=100, <=300, <=1000, <=3000, <=10000, >10000 мс. Непереданные окна хранятся в памяти до 30 минут. Полные структурированные логи остаются на хостинге. Ротацию/срок хранения логов нужно подтвердить в панели NetAngels при создании хостинга; приложение не управляет журналами хостинга.

## Первое размещение

1. В production-окружении GitHub задать Variables `MONITOR_BROWSER_URL`, `MONITOR_BROWSER_KEY`. Release — SHA коммита, задаётся workflow автоматически.
2. В приватном `app/shared/.env` на NetAngels записать серверные MONITOR_URL и MONITOR_KEY. Ключ бота приложению не нужен.
3. В конфигурации `coach-yuliya` общего сервиса указать реальные HTTPS origins сайта и админки. Добавить проверки сайта (HTTP 200 + стабильный текст) и API `/health/ready` (HTTP 200 + ожидаемое содержимое). До появления доменов targets остаются пустыми.
4. После деплоя отправить контролируемую ошибку в каждом компоненте, сверить release/request ID в экспорте, получить тестовую тревогу и восстановление в Telegram.

## Source maps и расследования ИИ

Workflow строит hidden source maps при `MONITOR_ARCHIVE_SOURCEMAPS=true`. Скрипт `sourcemaps.mjs` копирует их в приватный архив, удаляет из web-сборки, а `upload-sourcemaps.mjs` загружает по проверенному SSH в `<корень домена>/.source-maps/<SHA>/backend.tar.gz` либо `site.tar.gz`, вне `www`. Ошибка архивации/загрузки останавливает деплой. Удаление старых архивов — отдельная политика хостинга: сейчас сохраняются все размещённые версии.

ИИ получает выгрузку через read-only API общего сервиса и сопоставляет release со source maps и кодом Git. Данные не отправляются какой-либо модели автоматически. Красивый интерфейс ошибок не требуется, но исходные координаты и версии нужны даже ИИ. При необходимости для расследования дополнительно читаются полные серверные логи по SSH.

## Что ещё не означает «подключено»

Пока хостинга и production-доменов нет, работающий общий сервис не проверяет будущий сайт. Готовность его настройки и факт наблюдения за реальным production — разные состояния. Браузер может блокировать телеметрию, а проверка Cloudflare не доказывает доступность у каждого провайдера. Отказ самого Cloudflare потребует независимой проверки `/health`, если нужна защита и от этой общей точки отказа.
