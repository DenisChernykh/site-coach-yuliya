# Мониторинг production

Подготовлено к первому размещению. Пока нет production-доменов, хостинга и
подключённых аккаунтов, сбор и уведомления **не работают в проде**. Локальная
разработка и демо на GitHub Pages не отправляют события.

## Что обнаруживаем

| Ситуация                                                                              | Обнаружение и хранение                                                   | Уведомление                                                      |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| JavaScript-ошибка сайта или админки                                                   | Sentry: необработанные ошибки, rejected promises, ошибки React в админке | Отправитель читает Sentry каждую минуту и пишет в Telegram       |
| API возвращает 5xx, сеть недоступна, неверный JSON                                    | Клиентский Sentry; серверные исключения отдельно в Sentry                | Telegram со ссылкой на группу ошибок                             |
| Ошибка процесса API, фоновой доставки заявок или публикации                           | Pino JSON в логе хостинга, ошибка дополнительно в Sentry                 | Telegram                                                         |
| Недоступен сайт/API/админка, неверный TLS, база или Redis                             | HetrixTools, HTTP-проверки каждую минуту                                 | Telegram при падении и восстановлении                            |
| Остановился cron отправителя, сломан токен Sentry/Telegram, не записывается состояние | HetrixTools heartbeat после успешного цикла                              | Telegram от независимого бота HetrixTools примерно через 6 минут |

Внешняя HTTP-проверка подтверждает доступность, но не прохождение всех пользовательских
сценариев. Разовая ошибка браузера обнаруживается, когда пользователь исполняет этот
код. Блокировщик рекламы или отсутствие сети могут помешать доставке события в Sentry.
Фатальное завершение ОС/OOM может не успеть отправить событие; его покрывает uptime.

События содержат компонент, версию релиза, координаты стека, код ошибки и `requestId`.
Текст исключений, пользовательские данные, cookies, тела/заголовки запросов,
query-параметры, breadcrumbs и переменные стека удаляются. Для расследования
используйте стек с source maps, безопасный код ошибки и корреляцию с JSON-логом
сервера. Ожидаемые 4xx и отменённые клиентские запросы не создают инцидент.
Трассировка, replay и отправка всех логов в Sentry отключены.

## Стоимость и ограничения

Проверено по тарифам 26 октября 2026 года:

- [HetrixTools Free](https://hetrixtools.com/pricing/uptime-monitor/): 15 мониторов,
  интервал 1 минута, до 4 локаций, Telegram. Здесь используются 4 монитора.
  Нужно входить в аккаунт хотя бы раз в 90 дней; журнал активности Free — 15 дней.
- [Sentry Developer](https://sentry.io/pricing/): $0, один пользователь,
  5 000 ошибок в месяц, хранение 30 дней. При исчерпании квоты новые ошибки могут
  перестать сохраняться. Проверяйте Usage и оставьте уведомления Sentry о квоте.
- В бесплатном Sentry заявлены email-уведомления; здесь Telegram работает через
  собственный cron и API чтения, без покупки платной интеграции.
- Cron использует уже оплачиваемый хостинг NetAngels. Платные подписки этой
  настройкой не включаются. Тарифы могут измениться — перепроверьте при подключении.

В приложении ограничена отправка: до 20 событий в минуту на вкладку браузера и 60
на процесс API. Это защита от локальной лавины, а не глобальный месячный лимит.
Постоянная одна и та же ошибка повторно уведомляет не чаще раза в час. Несколько
групп объединяются в одно сообщение; первые 10 получают отдельные ссылки.

## 1. Sentry

1. Создайте организацию и один JavaScript-проект для сайта, админки и Node API.
   Компоненты различаются тегом `component=site|admin|backend`, окружение — `production`.
   Ограничьте Allowed Domains адресами сайта и API, включите удаление IP на стороне
   проекта. SDK не передаёт IP пользователя в поле `user`; сетевой адрес соединения
   всё равно виден сервису при приёме HTTPS-запроса.
2. Создайте GitHub Environment `production` по инструкции развёртывания проекта.
   Добавьте Variables: `SENTRY_DSN`, `SENTRY_ORG`, `SENTRY_PROJECT`.
   DSN предназначен для браузера и не является токеном управления.
3. Добавьте Secret `SENTRY_AUTH_TOKEN` с правами загрузки source maps/релизов
   выбранного проекта. Не используйте токен чтения уведомлений вместо него.
4. На хостинге задайте `SENTRY_DSN` процессу Node API. `NODE_ENV=production`;
   `SERVICE_REVISION` выставляет существующий загрузчик из `release.json`.
5. Создайте отдельный пользовательский API-токен `event:read` для отправителя.
   Сохраните как `SENTRY_READ_TOKEN` в приватном файле конфигурации cron.
   Проверьте доступ командой отправителя перед включением расписания: при 401/403
   проверка завершается ошибкой, heartbeat не отправляется.

Workflow требует настройки Sentry перед production-деплоем. Source maps создаются
только для production-сборки, получают debug IDs, загружаются в Sentry с Git SHA,
затем удаляются из пакета развёртывания. Ошибка загрузки останавливает деплой.
Исходный код из source maps доступен участникам проекта Sentry.

## 2. Telegram и HetrixTools

1. Создайте бесплатный аккаунт HetrixTools. Напишите `/start` официальному
   `@hetrixtools_bot`, получите Chat ID и добавьте Telegram в Contact List по
   [официальной инструкции](https://docs.hetrixtools.com/telegram-integration/).
   Отключите Do Not Disturb для аварийного контакта.
2. Скопируйте `monitoring/production.env.example` в игнорируемый `.env.monitoring`.
   Укажите настоящие HTTPS-origin сайта и API, без пути и query.
3. Получите точный план без секретов:

   ```sh
   node --env-file=.env.monitoring scripts/monitoring/verify-uptime.mjs --plan
   ```

4. Создайте в HetrixTools три Website-монитора из плана: `/`, `/health/ready`,
   `/admin/`. Интервал 1 минута; timeout 10 секунд; только HTTP 200; без redirects;
   проверка сертификата и имени; обязательная строка в ответе. Для сайта/API
   используйте 3 локации и подтверждение большинством (2 из 3), 3 попытки,
   уведомление через 1 минуту подтверждённого сбоя. Напоминания: 3 раза через час.
   После восстановления включены UP-уведомления. Привяжите Telegram Contact List.
5. Создайте четвёртый монитор `Coach Yuliya · error notifier`, тип Cron Job / Heartbeat,
   простой интервал: timeout 300 секунд, grace 60 секунд. Привяжите тот же контакт.
   Сохраните приватный URL `https://sm.hetrixtools.net/hb/?s=…` в
   `MONITOR_HEARTBEAT_URL`. URL не публикуется и не добавляется в GitHub Variables.
6. Все мониторы и адреса оставьте приватными (`public_report=false`, `public_target=false`).
   Для проверки задайте read-only `HETRIXTOOLS_API_KEY` с GET Uptime Monitors и
   GET Contact Lists. Скрипт сверяет состояние, свежесть проверок, TLS, настройки
   и Telegram. Текущий API v3 предоставляет чтение, создание выполните в панели.

   ```sh
   node --env-file=.env.monitoring scripts/monitoring/verify-uptime.mjs
   ```

Ожидаемая задержка DOWN — несколько минут с учётом расписания, timeout и подтверждения
локациями; ровно 60 секунд не гарантируется. Если аудит сообщает расхождение,
исправьте настройку, а не считайте наличие монитора достаточным.

## 3. Отправка ошибок из Sentry в Telegram

Для ошибок используйте отдельного бота, созданного в BotFather. Начните с ним чат
или добавьте в выбранную группу. Не используйте бота заявок клиентов: его сбой
должен приходить по отдельному каналу.

На хостинге создайте файл `app/shared/monitoring.env` с правами `0600`, недоступный
через HTTP, с полями `SENTRY_ORG`, `SENTRY_PROJECT`, `SENTRY_READ_TOKEN`,
`SENTRY_API_ORIGIN`, `MONITOR_TELEGRAM_BOT_TOKEN`, `MONITOR_TELEGRAM_CHAT_ID`,
`MONITOR_STATE_DIR`, `MONITOR_HEARTBEAT_URL` из шаблона. `MONITOR_STATE_DIR` —
абсолютный путь к `app/shared/monitoring`, который сохраняется при обновлении релиза.
Не копируйте сюда CI-токен `SENTRY_AUTH_TOKEN`.

Сначала вручную выполните на хостинге (замените пути на реальные):

```sh
/absolute/path/to/node --env-file=/absolute/app/shared/monitoring.env /absolute/app/current/scripts/netangels/notify-errors.mjs --test-telegram
/absolute/path/to/node --env-file=/absolute/app/shared/monitoring.env /absolute/app/current/scripts/netangels/notify-errors.mjs
```

Используйте абсолютный путь к Node 24 из виртуального окружения сайта: получите
его через `command -v node` после перехода в каталог сайта по SSH. Проверьте
`node --version` тем же путём. В NetAngels cron настраивается
[в панели сайта](https://www.netangels.ru/support/cloud-hosting/overview/), не через
обычный `crontab`. Добавьте вторую команду с расписанием `* * * * *`.

Скрипт запрашивает ошибки production за последние 24 часа, до 500 групп, отправляет
только безопасные ссылки и сохраняет подтверждённые доставки атомарно. После сбоя
Telegram отправка повторяется; после сбоя между доставкой и записью возможен дубль.
Первый запуск отправляет сводку за последние сутки. Повреждённое состояние,
ошибка API, переполнение лимита или таймаут завершают цикл ошибкой и не обновляют
heartbeat. Пропуски дольше 24 часов требуют ручного просмотра Sentry.

Heartbeat обновляется после успешного чтения, отправки требуемых сообщений и записи
состояния. При недоступности всего хостинга HetrixTools продолжает самостоятельно
проверять доступность и уведомлять. Код сайта не нужен для отправки этих аварий.

## Проверка перед открытием сайта

1. Вручную отправьте тест Telegram указанной командой и убедитесь в получении.
2. На тестовом развёртывании вызовите JavaScript-ошибку сайта и админки: убедитесь,
   что видны компонент, SHA релиза, исходный файл/строка, отсутствуют тестовые
   контакты и секреты; сообщение Telegram приходит после следующего cron.
3. Проверьте серверную ошибку и сбой доставки заявки на тестовом окружении:
   событие сохраняется, повторные одинаковые ошибки не создают поминутный спам.
4. Проверьте DOWN и UP на временном тестовом адресе HetrixTools, затем верните
   production-адрес и запустите аудит. Не отключайте рабочий прод ради теста.
5. Остановите cron на тестовом окружении: должна прийти авария heartbeat;
   после восстановления — UP. Не запускайте отдельный `curl` heartbeat вне скрипта:
   он скроет поломку отправителя.
6. Убедитесь, что `.map` нет в публичной сборке, `/health/ready` отвечает 200
   только при доступных PostgreSQL/Redis, все четыре монитора проходят аудит.

Локальные автоматические проверки: `pnpm test` (редакция данных, уведомления,
дедупликация, ошибки внешних API), `cd backend && pnpm check:quick`
(включает реальный SDK с перехваченным транспортом), `cd admin && pnpm check`.
Они не заменяют проверку реальной доставки после создания аккаунтов и хостинга.

## При аварии

Откройте ссылку Sentry из Telegram, проверьте `component`, `release`, стек и
`requestId`. Серверный JSON-лог NetAngels находится в `log/node-runlog/current`
в каталоге сайта; его ротация принадлежит хостингу, долговременное хранение ошибок
обеспечивает Sentry в пределах тарифа. Уведомление HetrixTools API означает также
возможную неисправность PostgreSQL/Redis. Авария `error notifier` требует проверки
cron, токенов, доступа к API и прав на `app/shared/monitoring`.

GitHub Actions используются для сборки, проверки и деплоя. Регулярные проверки
доступности выполняет HetrixTools: у scheduled Actions возможны задержки, а
в публичном неактивном репозитории расписание может отключиться через 60 дней.
Это не подходит как единственный канал обнаружения production-аварий.

Источники: [GitHub schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule),
[Sentry issues API](https://docs.sentry.io/api/events/list-an-organizations-issues/),
[HetrixTools heartbeat](https://docs.hetrixtools.com/how-to-use-the-cron-job-monitor/),
[NetAngels Node.js и логи](https://www.netangels.ru/support/cloud-hosting/node/).
